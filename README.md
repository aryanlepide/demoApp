# MiniDSP — 3-hour AI Developer Challenge (simplified)

**Objective:** Build a working, tested, documented MiniDSP web app using two GitHub Copilot chats and human judgement. This is a competition, not a compliance paperwork exercise.

## The entire workflow
1. Open the project in VS Code. Open GitHub Copilot Chat 1 in Ask mode (Instructor). Paste `START_HERE_INSTRUCTOR.md`.
2. Instructor proposes a small next task and gives a copy-ready prompt.
3. Paste that prompt into a separate GitHub Copilot Chat 2 in Agent mode (Developer). Agent implements, tests and records progress.
4. Paste Agent's response into Instructor. Instructor challenges assumptions, code, tests, security and gaps; gives a focused follow-up if needed.
5. Repeat until working; the human developer orchestrates, reviews and decides what to approve and when to commit/deploy.

**Don't paste raw uploaded file content, credentials or personal data into either AI chat.** Only synthetic training files may be used.

## Files
- `START_HERE_INSTRUCTOR.md` — paste once into Chat 1
- `START_HERE_DEVELOPER.md` — paste once into Chat 2, before its first task
- `PRODUCT_BRIEF.md` — functionality, safety and acceptance criteria
- `CHALLENGE_TIMELINE.md` — timeboxes and priority
- `DESIGN_REFERENCE.md` — facilitator fills in actual design-system paths and live URL
- `WORK_LOG.md` — Agent maintains short, honest progress/test/decision log
- `LEARNINGS.md` — Agent helps developer capture lessons
- `DEVELOPER_SCORECARD.md` — generated by the Agent at the end of the challenge only
- `FOR_SUNJEEV.md` — setup checklist and facilitator instructions
- `DEVELOPER_QUICK_GUIDE.md` — one-page instructions
- `tests/fixtures/` — starter synthetic files; optional withheld acceptance pack provided separately

## Current local prototype

This workspace began as the documentation-and-fixtures package described above. It now also includes a local prototype for the Login, Create account, Dashboard, Upload, and Findings screens. The prototype uses Node.js 24, the supplied synthetic fixtures, and the Lepidus CSS/JavaScript distribution. When Supabase is configured, Auth sessions are held in HttpOnly cookies and masked scan aggregates are stored in the RLS-protected `scan_records` table. Without Supabase environment variables, the app falls back to salted in-memory demo accounts and volatile scan history. Uploaded file contents are scanned in memory and never stored.

Run from PowerShell:

```powershell
npm.cmd run dev
npm.cmd test
```

Open `http://127.0.0.1:4173`. `npm.cmd run dev` serves the local prototype; `npm.cmd test` runs the detector, upload/API, and safe CSV export tests. The dashboard starts empty and updates after each successful scan. Scan history resets when the server stops or when **Reset demo** is selected.

### Supabase setup

1. Set `SUPABASE_URL` and `SUPABASE_ANON_KEY` in the ignored `.env.local` file. `.env.example` shows the variable names. Never use or commit a service-role key.
2. Apply `supabase/migrations/20261021000000_scan_records.sql` to the Supabase project using its SQL editor or migration workflow. The table stores filename, timestamp, risk, and masked aggregate findings only; RLS policies bind every row to `auth.uid()`.
3. Run `npm.cmd run dev` again. The server reads `.env.local` automatically. The login page identifies whether it is using Supabase or the local demo fallback.

The configured project is reachable: the Auth settings endpoint and the `scan_records` REST schema both returned HTTP 200 during verification, and the running app reports `authMode: supabase`. Live signup and owner-scoped inserts remain **UNVERIFIED** because email confirmation is enabled and no test mailbox/account is available. The automated suite exercises the local fallback and ownership boundaries; it does not substitute for a confirmed Supabase user session and database write.

### Vercel deployment

Vercel uses `api/[...path].ts` as the Node function entrypoint and `vercel.json` rewrites `/`, `/login`, `/signup`, `/dashboard`, `/upload`, and `/findings` to the static app shell. The function disables automatic body parsing so multipart uploads reach the server validator intact, and bundles the synthetic fixture directory for the sample-scan endpoint. Set `SUPABASE_URL` and `SUPABASE_ANON_KEY` in Vercel project environment settings before deployment; hosted mode refuses local in-memory auth when those variables are missing. Deployment itself is not verified until a Vercel build and live smoke test complete.
